## 这阶段做了什么

我们没有写服务器代码，而是先把“按钮按下后，谁能做什么、失败怎么办、怎样不串任务、AI 结果何时才算采用”写成施工蓝图。这样下一阶段写代码时，开发者只需要实现和验证，不用临时替你决定产品行为。

## 六个关键词

1. **API**：浏览器和后端约定好的办事窗口。它说明可以提交什么、会得到什么以及失败如何表达。
2. **Worker**：后台办耗时工作的进程。API 先收下任务，Worker 再处理网页、向量和 AI；浏览器不用一直卡住。
3. **事务**：一组数据库修改要么全部成功，要么全部撤销。例如保存问题、使下游待复核和记录审计必须一起完成。
4. **乐观锁**：保存时核对“你编辑的是否仍是最新版本”。另一窗口已经改过，就提示冲突，而不是互相覆盖。
5. **RAG**：先从当前任务允许的史料块里找相关原文，再把这些原文交给模型。它缩小模型凭空发挥的空间，但不自动保证答案正确。
6. **Agent/LangGraph**：把“检索—生成—校验—等待教师”这样的多步工作串起来并记住暂停位置。它不是有权限替教师决定的机器人。

## 为什么 API 和 Worker 要分开

保存文字通常很快，适合 API 在短事务里完成；网页和 AI 可能慢、超时或需要重试，适合 Worker。两者通过 PostgreSQL job 交接，所以即使程序重启，也能知道工作做到哪里。

## 为什么 AI 结果先是建议

模型可能格式错误、引用错位，也可能在生成期间教师已经修改任务。建议先放在不可变版本里，教师采用时再重新核对最新任务和引用，才能避免旧答案覆盖新工作。

## 常见坑

- 有 task ID 不代表有权限；任何人都能猜或复制 ID。
- “模型返回了 JSON”不代表内容符合业务规则，仍要 Zod、引用和权限校验。
- SSE 只是进度广播，不是数据库真相；断线后必须重读状态。
- Worker 的任务可能重跑，因此只能承诺结果最多应用一次，不能谎称外部调用绝不会重复收费。
- 删除数据库 task 不等于 checkpoint 自动消失，必须显式整线程清理。
- localhost 不等于天然安全，仍需 Cookie、Host/Origin、CSRF 和 SSRF 防护。

## 你可以亲自检查

打开 `API-AND-OPENAPI-DESIGN.md`，任选一个写操作，检查它是否同时回答了：谁能调用、输入是什么、版本冲突怎样提示、重复点击怎样处理、是否会产生费用、失败后现有数据是否保留。若其中一项找不到，说明设计还不能直接编码。
