# 史证工坊就绪与完成定义（DoR / DoD）

> 文档版本：0.3
> 更新日期：2026-08-31
> 状态：0.3 已批准归档

## 1. 使用方法

DoR 回答“能否开始”，DoD 回答“能否报告完成”。两者都是检查门禁，不是形式清单。任一必需项为“未知”即未满足；确属不适用时必须写明理由。用户的“批准归档”只认可当前阶段成果，不授权下一层、公开发布、购买、push 或部署。

## 2. 通用 DoR

开始非简单子阶段前必须满足：

- 当前阶段、目标、允许和禁止路径已写入 `PROJECT-STATE.md`；上游文档均已批准归档。
- 需求 ID、用户、成功标准、范围与非范围明确，术语与 `PROJECT-HANDBOOK.md` 一致。
- 输入、输出、接口边界、数据分类、参与者/权限和信任边界已说明。
- 正常、失败、未认证、无权、边界、重复、取消/恢复的预期已明确或标记不适用。
- 测试方法、验收命令、人工证据、风险、费用和回滚/删除路径可执行。
- 相关外部资料已核验；新增依赖、付费、真实数据或公开动作已有单独授权。
- Git 起点和已有用户改动已检查，工作区冲突有处理方案。

缺少会改变范围、权限、数据生命周期、费用或外部副作用的决定时必须停下询问；不以自行假设填补。

## 3. 分阶段 DoR

| 阶段类型 | 额外就绪条件 |
|---|---|
| 设计阶段启动 | 上一阶段全部编码/规划完成并归档；待设计问题、案例检索范围、现有 Skill/工具盘点和明确不设计内容列出；没有提前实现 |
| 设计决策定稿 | 已完成该层至少3个成熟 GitHub 案例及官方资料研究，满足 `MASTER-PLAN.md` 的高星/维护/许可规则并形成采纳、调整、淘汰映射；能力缺口对应的 Skill/插件已按规则处理；已按 `DESIGN-REVIEW-STANDARD.md` 通过完备性门和编码就绪门 |
| 前端编码 | 页面、组件、状态、视觉、响应式、无障碍、前端视图模型/data adapter、Mock/fixture 和验收规格已批准；`FRONTEND-REVIEW` P0 为零 |
| 数据库编码 | ERD、字段、约束、权限/RLS取舍、索引、迁移、种子、删除/恢复方案已批准；`DATABASE-REVIEW` P0 为零 |
| 后端编码 | OpenAPI、用例、授权、任务/Worker、AI/RAG/Agent、错误/限额/失败方案已批准；`BACKEND-REVIEW` P0 为零 |
| 集成 | 前端、数据库、后端各自编码全部完成并归档；共同契约版本锁定 |
| 发布 | 质量/安全验收已通过；公开目标、权限、回滚点、费用和秘密清单经单独授权 |

## 4. 通用 DoD

一个实施阶段只有同时满足以下条件才可报告“完成”：

- 批准范围内的产物全部存在，范围外没有顺手实现；需求和风险可追踪到文件/测试。
- 当前环境运行约定的最窄测试及风险相称的广泛测试，完整记录命令、退出码、通过/失败/跳过。
- 安全、权限、数据、错误、无障碍、成本和恢复要求有对应代码/设计与证据；阻断级问题为零。
- 文档、示例、配置清单、迁移/回滚/删除说明与实际实现同步；不存在占位符、假数据冒充真实能力或未披露缺口。
- `git status` 和完整差异已复核，只包含获批路径，未暴露秘密/真实数据，未安装或修改无关内容。
- 阶段报告包含成果、学习卡、来源、验证证据、文件清单、遗留风险和建议提交消息。
- 用户尚未批准时状态只能是“待用户批准归档”；不得暂存、提交、打标签、push 或开始下一阶段。

## 5. 产物特定 DoD

### 5.1 文档/设计

- 输入、决策、理由、淘汰项/非范围、边界状态、验证方法和重新评估条件齐全。
- 设计草案完成后按 `DESIGN-REVIEW-STANDARD.md` 从上游意图重新审查；完备性和编码就绪分别给出证据，不以文件数、章节数或模型自评代替。
- REVIEW 包含 `hard-freeze`、`bounded-flex`、`deferred-blocker` 决定表和 P0/P1/P2 发现；P0 为零，P1 已解决或有用户批准的明确例外。
- 前端、数据库或后端设计附案例研究表：仓库 URL、访问日期、Star 快照、版本/提交、维护状态、测试/CI、文档、许可证、适用性和不能照搬处；结论可追踪到本项目需求与风险。
- 至少3个相关成熟案例且原则上至少2个达到研究日5,000 Stars；不满足时必须提供细分领域检索证据和经用户批准的书面例外。
- 工具能力记录列明已复用和新安装的 Skill、搜索候选、来源/Star/维护/许可、固定版本、安装范围、权限、验证和卸载方式；没有新增时说明现有能力为何足够。
- 任何插件账号连接或权限变化都有用户确认记录；Skill/插件没有被误写成应用依赖，也没有未经批准进入公开仓库。
- 图表有文字说明，链接有效，版本/日期/状态一致；与上游无冲突。
- 评审明确回答：可执行性、是否过度设计、阻塞项、下一阶段是否仍需发明高代价决定、是否允许进入下一阶段。

### 5.2 代码

- 实现符合依赖方向和契约，无空 catch、硬编码秘密、跨层规则复制或测试绕过。
- 新行为有回归/行为测试；静态、单元及当前层适用的集成/E2E/build 均通过。
- 错误、日志、配置、取消、幂等、限额和清理行为已验证，而非只覆盖成功路径。

### 5.3 数据库

- 空库建库、逐版升级、约束/索引、并发/事务、跨任务隔离和级联删除测试通过。
- 迁移失败的前滚/回滚路径与备份恢复演练有证据；合成种子不含真实数据。

### 5.4 发布

- 干净环境可复现构建；Public 仓库与 Pages 精确目标获授权并实际验证。
- 秘密、许可、链接、浏览器、可访问性、中国网络抽样、回滚和运维手册均通过检查。
- Demo 与完整模式能力边界在页面和 README 中诚实可见。

## 6. 不构成完成的证据

- “代码看起来正确”、只跑单个快乐路径、旧会话输出、被跳过测试、模型自评或没有退出码的截图。
- 达到覆盖率数字但关键规则无直接断言；构建成功但运行/权限/删除未验证。
- 把风险写进待办而不说明影响、负责人和重新评估门槛。
