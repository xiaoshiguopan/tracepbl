# 设计完成后审查规范

> 文档版本：0.1
> 更新日期：2026-08-31
> 状态：已批准归档
> 适用阶段：阶段 5 前端设计、阶段 7 数据库设计、阶段 9 后端设计

## 1. 目的与门禁

本规范回答的不是“设计文档是否都存在”，而是“下一编码阶段是否无需临场补做高代价产品或架构决定”。三层设计都必须在草案完成后、阶段报告和批准申请前单独执行一轮第一性原理审查；产物数量、章节齐全、模型自评或案例数量均不能代替编码就绪证据。

固定顺序：

```text
上游意图与约束
→ 当前层设计草案
→ 第一性原理设计后审查
→ 修订阻断与高返工缺口
→ 复验
→ 层级 REVIEW + 阶段报告
→ 用户批准归档
→ 对应层编码
```

审查不得提前设计下一层。当前层只能记录下游必须满足的可观察契约、约束和验证问题，不能借审查提前定义数据库表或具体后端 API。

## 2. 第一性原理审查问题

审查者必须脱离“已有文档写了什么”的顺序，从上游目标重新回答：

1. **结果**：目标用户或下游消费者最终要完成什么可观察结果？
2. **真相与不变量**：哪些事实、状态、约束和信任边界绝不能被表现层或便利实现改写？
3. **失败**：空、错、慢、断、重复、并发、越权、部分成功和恢复时，系统必须保留什么、阻断什么、告诉谁？
4. **高代价决定**：哪些未决定项会迫使下一阶段重做结构、公共契约、迁移、权限、核心测试或主要界面？
5. **可执行性**：下一阶段能否只做实现判断，而不用发明新的产品行为、状态语义或安全规则？
6. **证据**：结论由什么原型、计算、追踪、演练、案例、负面场景或当前命令输出证明？

“原则上支持”“编码时再看”“后续优化”不能回答上述问题；若该决定影响高返工面，必须在本层解决或作为阻断报告。

## 3. 两道完成门

### 3.1 完备性门

- 计划产物存在，输入、决策、非范围、状态、错误、权限、数据、验证和风险可追踪；
- 当前官方资料与成熟案例研究完成；
- 文档、模板、索引、状态和 Git 范围一致；
- 没有占位符、伪证据、真实敏感数据、无权材料或范围外实现。

### 3.2 编码就绪门

- 高返工决定已经冻结；可逆细节明确允许在编码中调整；
- 跨产物状态、术语、字段、契约、约束和失败语义无冲突；
- 复合状态、边界规模、并发/重复、降级和恢复已演练；
- 下一阶段输入足以建立代码、测试和 Mock/迁移/契约，不需要猜测产品意图；
- P0 为零；P1 已解决，或由用户书面接受例外、负责人、触发条件和最晚解决点；
- REVIEW 明确列出仍可留到编码期的低代价细节，不用“全部完成”掩盖未知。

只有两道门都通过，才能申请进入对应编码阶段。

## 4. 审查方法

1. **重建意图**：从 PRD、技术决策、总规划、已批准上一层实现和当前状态重建用户结果、非目标与硬约束。
2. **盘点设计**：建立“要求 → 设计决定 → 失败/边界 → 验证证据 → 文件位置”追踪表。
3. **决定冻结表**：逐项标记 `hard-freeze`、`bounded-flex` 或 `deferred-blocker`。
   - `hard-freeze`：编码改变会影响核心流程、公共契约、数据完整性、权限、安全、迁移或大面积组件。
   - `bounded-flex`：允许编码期在明确范围内调整，如细微间距、局部命名或无行为影响的内部结构。
   - `deferred-blocker`：尚未决定且会造成高返工；解决前不得批准。
4. **对抗性走查**：覆盖正常、空、失败、边界、重复、并发、取消、超时/离线、部分成功、越权、恢复和上游变更；检查多状态同时出现时的优先级。
5. **交叉影响审查**：核对当前层对已批准上游的兼容性，并只记录下游约束，不提前设计下游实现。
6. **证据验证**：使用与风险相称的原型、样例、静态计算、契约示例、状态/迁移演练、负面测试计划和当前 Git/文档检查；无法验证的项目标为未知。
7. **分级修订**：先处理 P0，再处理 P1；修订后重新执行受影响检查，不沿用旧结论。
8. **形成结论**：对应 `FRONTEND-REVIEW`、`DATABASE-REVIEW` 或 `BACKEND-REVIEW` 必须引用本规范并给出证据，而不是只勾选清单。

审查可以由同一执行者进行，但必须重新从上游意图推导，不能只证明自己的草案内部自洽。第二代理、工具或案例可以发现问题，但其自评不能替代项目证据和用户批准。

## 5. 发现分级

| 等级 | 定义 | 处置 |
|---|---|---|
| P0 阻断 | 可能造成错误产品行为、安全/权限缺口、数据损坏、不可逆迁移、公共契约重做或主要流程/架构返工 | 当前设计阶段解决并复验；不得申请编码 |
| P1 高返工 | 不立即危及安全，但会导致多个页面/组件、表/迁移、接口/Worker 或测试体系重做 | 原则上当前阶段解决；例外须用户书面接受并给最晚解决点 |
| P2 有界细节 | 修改局部、可逆、不改变公共行为或跨层约束 | 可列入编码期验证，不冒充遗漏已解决 |

风险清单必须写影响面、证据、建议决定、负责人和重新评估触发条件。只写“后续关注”不合格。

## 6. 各层最低审查面

### 6.1 前端设计

- 用户任务、信息架构、页面职责、导航/URL、逐页布局和跨页返回；
- 正常与复合状态的优先级、异步竞态、草稿/冲突/恢复；
- 字段字典、控件、校验、完整界面文案和成功/错误反馈；
- 视觉方向、代表页面高保真、令牌实际对比度、图标/资产政策和用户审美批准；
- 响应式重排、长内容、触控、键盘、焦点、读屏、缩放和减少运动；
- 组件职责、全部交互状态、状态归属和页面—组件复用边界；
- 前端视图模型、adapter 能力、Mock/fixture 可执行结构；它们不是数据库 Schema 或具体后端 API；
- 目标浏览器、路由/存储降级、性能预算、大列表和资源加载；
- 代表性桌面/手机原型、关键失败原型、教师/用户走查及未验证限制。

### 6.2 数据库设计

- 已实现前端契约所需的实体、关系、所有权、基数、可空性、状态和历史版本；
- 可由数据库强制的不变量、唯一性、引用完整性、来源/加工可追溯性和审计完整性；
- 任务隔离、权限/RLS 取舍、敏感级别、最小访问和拒绝场景；
- 查询/写入路径对索引、约束和规模假设的证据；不建猜测性索引；
- 事务边界、并发冲突、幂等、重复、部分失败和死锁/重试策略；
- 创建、更新、过期、清除、级联删除、向量/对象/缓存残留和恢复生命周期；
- 空库、逐版升级、失败前滚/回滚、备份恢复、种子与合成测试数据演练；
- 与已批准前端实现/契约的差异及影响，不静默迫使前端改行为。

### 6.3 后端设计

- 用例、模块边界、依赖方向及 OpenAPI/公共契约与既有前端、数据库的一致性；
- 每个读取和动作的认证、逐资源授权、所有权、输入校验、错误和不泄露语义；
- 幂等、并发冲突、事务协作、重复请求和部分成功；
- 异步任务状态、进度、取消、超时、有限重试、恢复、过期结果和重放；
- 外部来源、文件、AI/RAG/Agent 的不可信输入、引用完整性、工具最小权限和人工门禁；
- 限流、额度、Token/费用、熔断、降级和 kill switch；
- 日志脱敏、追踪、指标、告警、审计事件和故障定位；
- 契约、权限负向、故障注入、Agent replay、性能和集成测试计划；
- 发布/回滚对现有前端和数据库的兼容窗口，不静默改变已批准行为。

这些条目是未来相应阶段的审查问题，不是对数据库或后端设计的提前授权。

## 7. REVIEW 必需输出

每层最终 REVIEW 至少包含：

1. 依据、版本、范围、非范围和审查日期；
2. 第一性原理重建：用户/消费者结果、不变量、主要失败；
3. 完备性门与编码就绪门的逐项结论；
4. `hard-freeze` / `bounded-flex` / `deferred-blocker` 决定表；
5. P0/P1/P2 发现、修订和复验证据；
6. 需求—设计—失败—证据追踪；
7. 跨层兼容性与明确未提前设计内容；
8. 未验证项、风险、负责人和触发条件；
9. 是否允许进入对应编码阶段，答案只能是“是”或“否”并附理由。

阶段报告必须与 REVIEW 结论一致。REVIEW 为“否”时，`PROJECT-STATE.md` 不得写“等待批准归档”，更不能开始编码。

## 8. 批准后变化

批准归档冻结的是 `hard-freeze` 决定和已声明的 `bounded-flex` 边界，不意味着设计永不改变。实现证据推翻假设时，按 `CHANGE-CONTROL.md` 分级：局部可逆细节在当前编码阶段验证；核心流程、状态、字段、公共契约、权限、数据生命周期或运行方式变化必须退回对应设计阶段重新审查和批准。
