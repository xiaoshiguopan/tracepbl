## 2. 跨文档可执行性

- 每阶段都有输入、输出、验收和用户门禁；DoR/DoD 与变更控制能阻止提前进入下一层。
- 浏览器→API、API→Worker、Worker→模型/检索、应用→数据库/存储、CI→发布的信任边界均有权限和测试落点。
- 当前无应用代码/测试的事实已明确；标准命令和测试能力均写为后续计划，没有虚构通过结果。
- Agent 的提示引导与应用硬规则分开；授权、删除、费用、引用门禁和教师批准不交给模型。
- Demo 与完整模式共享领域/契约，但数据源、秘密和公开承诺分离，避免用假后端误导求职展示。
- 前端、数据库、后端设计都必须先完成当时的 GitHub 成熟案例研究；Star 门槛配合维护、测试、文档、许可和安全信号，避免把流行度误当正确性。

## 3. 过度设计检查

本阶段只确定跨层规则，没有确定具体页面、组件树、字段、表、索引、API 路由、Agent 图节点、云厂商或域名。以下能力明确不在 v0.1：账户、学生端、管理后台、邮件、支付、入站 webhook、定时 cron、真实数据和生产完整后端。后续只有出现批准需求时才能加入。

采用单仓库、模块化单体 API 与单 Worker，不引入微服务、消息总线或多云抽象。文件行数等门槛用于触发审查而非机械拆分。
